# Clase 9 — Modificabilidad (Modifiability)

## Preguntas guía

- ¿Qué puede cambiar? funciones, plataforma, entorno (otros sistemas),
  otros atributos de calidad.
- ¿Qué tan probable es el cambio?
- ¿Quiénes pueden hacer el cambio? desarrolladores, administradores,
  usuarios finales.
- ¿En qué momento? en desarrollo, en producción.
- ¿Cuánto cuesta? sistema flexible pero costoso de desarrollar vs. sistema
  que requiere cambios de los desarrolladores pero es menos costoso.

## Atributos relacionados

- **Escalabilidad** (mencionada sin desarrollar más).
- **Variabilidad**: capacidad del sistema de crear variaciones a la
  funcionalidad original (ej. variación por tipos de licencia, líneas de
  producto).
- **Portabilidad**: capacidad de desplegarse en diferentes plataformas.
- **Independencia de ubicación**: capacidad de dos partes de un sistema de
  interactuar independientemente de dónde estén desplegados.

## Tácticas (Bass/Kazman)

Tres grupos: **Increase Cohesion**, **Reduce Coupling**, **Defer Binding**.

### Incrementar cohesión
- **Dividir módulos**: un módulo grande probablemente tiene baja cohesión;
  descomponer por funcionalidades conceptualmente cercanas.
- **Redistribuir responsabilidades**: buscar funcionalidades conceptualmente
  cercanas pero dispersas en el código, integrarlas en un componente
  independiente.

### Reducir acoplamiento
- **Encapsular**: a nivel de un componente individual (definir interfaz,
  ocultar internos, toda interacción pasa por la interfaz) y a nivel de
  varios componentes (exponer solo interfaces relevantes, ocultar internos
  no necesarios).
- **Usar intermediarios (Indirection)**: crear un componente que actúe como
  intermediario con el exterior para un grupo de componentes; todas las
  peticiones deben pasar por él. Patrones relacionados: Controller, Facade.
  Ejemplos: colas de mensajes, servicios en general.
- **Abstraer servicios comunes**: crear una interfaz abstracta común para
  dos o más servicios similares, complementada con un intermediario.
  Ejemplos: JDBC, Hardware Abstraction Layers (HAL)/drivers, servicios de
  pago online.
- **Restringir dependencias**: después de encapsular, restringir qué grupos
  de componentes se pueden comunicar entre sí y en qué dirección. Ejemplo:
  restricciones del modelo N-Tier (solo comunicarse con la capa
  inmediatamente inferior). Diferencia con Intermediario: son restricciones
  que normalmente no se pueden controlar desde el lenguaje de programación.

### Postergar enlace (Defer Binding)
Binding = conectar una interfaz con su implementación. Postergar enlace
flexibiliza cómo/cuándo ocurre esa conexión (a veces desacoplando interfaz
de implementación). Tácticas específicas:
- Binding en tiempo de compilación (ej. configure + Makefile).
- Binding en tiempo de ejecución: Service Discovery (ej. Spring Cloud
  Eureka), Interpretar parámetros/archivos de configuración (ej. Spring Boot
  application properties, command-line arguments), Repositorios
  compartidos/colas de mensajes (Redis, etcd en Kubernetes para
  configuración centralizada; Kafka), Polimorfismo.

## Patrones de Modificabilidad

Nota del profesor: todos los estilos arquitectónicos aportan a
modificabilidad; el deck se enfoca en los más evidentes.

- **Layered / N-Tier**: sistema dividido en N capas (presentación, negocio,
  persistencia, base de datos), cada capa se comunica solo con la
  inmediatamente inferior (evitar "bridging"/saltarse capas). Ventajas:
  reduce acoplamiento, facilita sustituir capas. Desventajas: overhead de
  comunicación entre capas (incluso en monolitos), puede ocultar funciones
  de bajo nivel útiles (ej. ORM vs SQL), el bridging dificulta mantenimiento.
- **Service-based**: servicios "gruesos", relativamente independientes,
  desplegables independientemente, pueden tener replicación y balanceo de
  carga; base de datos centralizada (lo más común), una BD por servicio, o
  múltiples BD compartidas entre algunos servicios; recomendable un único
  punto de entrada (API layer/proxy/gateway); se complementa con
  Layered/N-Tier.
- **Event-driven Architecture (EDA) / Message-driven Architecture (MDA)**:
  colas o publish-subscribe para enviar eventos y mensajes, ambos
  asíncronos. Eventos: describen algo que sucede, unidireccionales
  (fire-and-forget), múltiples consumidores. Mensajes: describen una orden
  que otro componente debe atender, requieren respuesta, típicamente un solo
  consumidor. Componentes: Emisor, Evento/mensaje inicial, Broker o Bus,
  Procesador/receptor, Evento/mensaje derivado.
- **Microkernel** ("Plug-in architecture"): núcleo con funcionalidades
  mínimas (Core system), funcionalidades adicionales (plugins) se instalan
  después, normalmente por el usuario final. Ejemplos: sistemas operativos
  (QNX), aplicaciones con funcionalidad base (IDEs, navegadores), apps web
  (Trello, Jira), videojuegos (Minecraft).
