# Clase 7 — Desplegabilidad (Deployability)

## Conceptos base

**Release**: entrega de software, versión estable lista para producción. En
el pasado poco frecuente; hoy muy frecuente (hotfixes, adaptación rápida a
cambios).

**DevOps → CI/CD**: Continuous Integration + Continuous Deployment. Pipeline
automatizada que lleva el código fuente hasta la plataforma de producción.

### CI/CD Pipeline — ambientes
1. **Development Environment**: computador del desarrollador (IDE,
   compiladores, pruebas unitarias, algunas de integración); guarda el
   código del módulo en el repositorio.
2. **Repositorio de código**: guarda el código de todos los módulos, control
   de versiones.
3. **Integration Environment**: servidor(es); integra todos los módulos —
   compila, empaqueta, ejecuta pruebas unitarias/integración/sistema.
4. **Staging Environment**: servidor(es); ejecuta pruebas de desempeño,
   disponibilidad, seguridad, validación/aceptación.
5. **Production Environment**: servidor(es) con acceso a usuarios finales;
   despliegue con patrón Shadow → Monitoreo → Reintroducción (visto en la
   clase de Disponibilidad).

Todo el pipeline se apoya en **Monitoreo** (mismo concepto visto en
Disponibilidad).

### Calidad de un pipeline
- **Tiempo de Ciclo (Cycle Time)**: tiempo desde especificación hasta
  despliegue de un requisito en producción.
- **Trazabilidad**: rastrear todos los elementos que dieron vida a un
  componente (código fuente, librerías, casos de prueba, herramientas).
- **Repetibilidad**: mismos resultados a partir de la misma acción sobre los
  mismos artefactos ("pero si en mi computador funcionaba!").

## Desplegabilidad — definición

Capacidad de un software de ser desplegado (instalado en un ambiente para
ejecución) con tiempo y esfuerzo razonables y predecibles.

### Problemas y preguntas de diseño
¿Cómo se empaqueta? ¿Cómo se envía al nodo donde se ejecutará? ¿Cómo se
integra con el resto del sistema? ¿Qué tanto control sobre el proceso de
despliegue? ¿Qué tan eficiente es el despliegue? — organizados en:
**Granularidad** (componentes vs sistema completo), **Controlabilidad**
(cómo se despliega, monitoreo del despliegue y de la ejecución),
**Eficiencia** (rapidez, nivel de esfuerzo, consumo de recursos).

## Tácticas de Desplegabilidad (Bass/Kazman)

Dos grupos:
- **Manage Deployment Pipeline**: Scale Rollouts, Script Deployment
  Commands, Rollback.
- **Manage Deployed System**: Manage Service Interactions, Package
  Dependencies, Toggle Features.

### Administración del pipeline de despliegue
- **Scaled Rollouts**: servicio nuevo se aplica a un subconjunto de usuarios,
  transición gradual.
- **Rollback**: si el nuevo servicio falla, volver a la versión anterior.
- **Scripts de despliegue**: automatizar todo lo automatizable; son código
  fuente más en el sistema (requieren programar, documentar, revisión de
  código, testing, control de versiones — "en casa del herrero...").

### Administración del sistema desplegado
- **Administrar interacciones entre servicios**: habilitar despliegue de
  distintas versiones de un servicio simultáneamente — service registry,
  traffic splitting, load balancing, circuit breaker.
- **Empaquetar dependencias**: empaquetar software junto con librerías, SO,
  entornos de ejecución — static linking, contenedores, Pods (Kubernetes),
  máquinas virtuales.
- **Activar/desactivar características ("Kill Switch")**: si una nueva
  característica falla, se puede desactivar en tiempo de ejecución (feature
  toggle).

## Patrones para Desplegabilidad

- **Estructuración de Servicios**: desplegabilidad independiente — asegurar
  que cada componente se pueda desplegar de forma autocontenida (empaquetar
  dependencias + administrar interacciones entre servicios).
- **Reemplazo total de servicios**:
  - **Blue/Green**: instalar instancias del nuevo servicio (Green) junto a
    las del antiguo (Blue) → redireccionar tráfico al nuevo → si funciona,
    remover el antiguo. Mejora disponibilidad; requiere 2×N instancias;
    período explícito para detectar errores; menos probabilidad de
    inconsistencias.
  - **Rolling Upgrade**: reemplazar instancias del servicio antiguo una a la
    vez por instancias nuevas. Mejora disponibilidad; requiere solo N+1
    instancias; errores detectables durante el upgrade; pero puede haber
    inconsistencia temporal o de interfaces (ambas versiones coexistiendo).
- **Reemplazo parcial de servicios**:
  - **Canary Testing**: designar un subconjunto de usuarios ("canarios":
    beta testers, usuarios internos o aleatorios), asignarles la nueva
    versión (scaled rollout), enrutamiento selectivo; actualización final
    vía Blue/Green o Rolling Upgrade. Pruebas con usuarios reales, exposición
    y costos reducidos, pero requiere planeación cuidadosa y enrutamiento
    selectivo.
  - **A/B Testing**: sistema antiguo (A) vs nuevo con cambios menores (B);
    se comparan métricas para elegir un "ganador" y descartar el "perdedor".
    Permite experimentar con usuarios reales, pero implica esfuerzo extra
    para implementar y caracterizar/seleccionar usuarios.
