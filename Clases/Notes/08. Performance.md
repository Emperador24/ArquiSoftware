# Clase 8 — Desempeño (Performance)

## Definición

`Performance = Tiempo + Espacio`.

### Principales problemas de desempeño
El mundo real tiene límites: procesos requieren tiempo > 0 para completarse,
recursos (memoria, disco) son limitados, redes tienen ancho de banda y
latencia, y los procesos dependen de otros elementos (disponibilidad de
recursos — servicios/hardware habilitados o deshabilitados, recursos
compartidos bloqueados por otros procesos — y dependencia hacia otros
procesos).

## Tácticas para Desempeño (Bass/Kazman)

Dos grupos: **Control Resource Demand** y **Manage Resources**.

### Controlar demanda de recursos
Dos preguntas guía: ¿cómo manejar la recepción de eventos en el sistema? y
¿cómo procesar los eventos una vez ingresan?

- **Administrar peticiones de trabajo (Manage Work Requests)**: gestionar la
  llegada de eventos vía SLA (procesar N eventos por unidad de tiempo,
  tiempo de respuesta máximo T); ajustar tasa de muestreo/procesamiento
  (tasa de recepción de datos de un sensor, frames per second, respuesta a
  peticiones por segundo).
- **Limitar respuesta a eventos (Limit Event Response)**: cuando llegan
  muchos eventos, encolarlos hasta poder procesarlos o descartarlos si
  pasan de cierto límite; preguntas: ¿qué tan crítico es procesar todos los
  eventos?, ¿qué hacer al descartar uno? (nada, logging, notificar a un
  usuario).
- **Priorizar eventos (Prioritize Events)**: procesar primero los más
  prioritarios, postergar o descartar los menos importantes.
- **Reducir overhead computacional (Reduce Computational Overhead)**:
  reducir indirección/intermediarios (hole punching en P2P/VoIP/VPN, C++
  inlining y devirtualization, linked lists → arrays); co-ubicar recursos
  que se comunican intensivamente (misma red o mismo nodo computacional);
  limpieza periódica (Postgres VACUUM, reboot).
- **Limitar tiempos de ejecución (Bound Execution Times)**: limitar cuánto
  tiempo de procesador usa un proceso (ejemplos Linux: cpulimit, cfs).
- **Aumentar eficiencia (Increase Efficiency)**: todo lo visto en Análisis de
  Algoritmos y Bases de Datos — código: buscar algoritmos más eficientes,
  revisar código con muchos ciclos, usar Map/Set donde sea necesario,
  profiling; bases de datos: usar índices, denormalizar donde la velocidad
  sea crítica.

### Administrar recursos
- **Aumentar recursos (Increase Resources)**: aumentar cantidad/capacidad de
  CPU y memoria; mejorar conexión de red.
- **Introducir concurrencia (Introduce Concurrency)**:
  - **Paralelismo**: procesar peticiones en paralelo en un mismo nodo
    computacional (¿qué procesos son paralelizables?, ¿tienen acceso a
    recursos compartidos?).
  - **Múltiples nodos computacionales**: réplicas, delegar peticiones a los
    nodos más disponibles.
- **Mantener múltiples copias de datos (Maintain Multiple Copies of Data)**:
  - Replicación de datos: copias en múltiples nodos similares (replicación
    de BD, sincronización).
  - Caching: copia de datos en almacenamiento más rápido (RAM vs disco,
    local vs remoto) — ejemplos: Redis, Memcached, Spring Boot Cache, CDN,
    caché del navegador, caché L1/L2/L3 de CPU.
- **Limitar tamaño de colas (Bound Queue Sizes)**: relacionado con "Limitar
  respuesta a eventos" — tamaño máximo de cola; qué hacer cuando se llena
  (descartar + logging, aumentar tamaño).
- **Programar recursos (Schedule Resources)**: determinar cuándo se usará un
  recurso según urgencia (scheduling de procesadores en el kernel de SO,
  scheduling de paquetes en la red / traffic shaping, buffers de escritura
  de archivos p. ej. en USB drives).
- Nota: "Mantener múltiples copias de cómputos" aparece en el árbol de
  tácticas oficial pero no se detalló explícitamente en las diapositivas más
  allá del diagrama inicial.

## Patrones de Desempeño

- **Balanceador de Carga (Load Balancer)**: redirige peticiones según
  disponibilidad de cada réplica (táctica: Schedule Resources). Ventajas:
  encapsula fallos en réplicas, reduce latencia, facilita escalabilidad.
  Desventajas: punto único de fallo, potencial cuello de botella.
- **Throttling**: limita la cantidad de peticiones que recibe un servicio
  (tácticas: Administrar peticiones de trabajo, Circuit Breaker). Ejemplos:
  Spring Cloud Gateway, Bucket4j, Nginx, throttling de mensajes en Kafka.
  Ventaja: reduce probabilidad de sobrecarga. Desventajas: potencial cuello
  de botella, se pueden perder peticiones si la demanda es muy grande,
  dificultad de agregar en sistemas existentes.
- **Map-Reduce**: procesamiento paralelo de datos. Map: aplica una función
  (Mapper) a una lista/stream de datos de entrada. Reduce: aplica una
  función de consolidación (Reducer) para producir datos consolidados.
  Ventajas: eficiencia para grandes datos, fallos afectan solo una parte del
  procesamiento. Desventajas: overhead podría no justificarse para datos
  pequeños, no sirve si no se puede paralelizar el procesamiento.
