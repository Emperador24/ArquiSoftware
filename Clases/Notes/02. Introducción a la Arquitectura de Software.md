# Clase 2 — Introducción a la Arquitectura de Software

## Arquitectura

Abstracción de alto nivel: omitir detalles innecesarios, enfocarse en lo
esencial. Arquitectura = **Estructura** (componentes, propiedades/atributos,
conexiones) + **Comportamiento** (cómo cambia en el tiempo).

## Vistas arquitectónicas

Ejemplo: modelo **4+1** (Logical, Development, Process, Physical view +
Scenarios). Ver también nota de la clase 4.

## Arquitectura vs Diseño detallado

| Decisiones arquitectónicas | Decisiones de diseño detallado |
|---|---|
| Largo plazo | Corto plazo |
| Impacto general | Impacto acotado |
| Cambios requieren mayor esfuerzo | Cambios requieren menor esfuerzo |
| Estratégica | Táctica |

## Atributos de calidad (glosario)

- **Availability**: el sistema responde cuando se requiere. Incluye
  Reliability, Recovery, Fault-tolerance. Fallos: prevención + detección +
  recuperación.
- **Deployability**: qué tan fácil es poner en producción una nueva versión
  (pasos manuales vs automáticos, CI/CD, ambientes: desarrollo/pruebas/producción).
- **Energy efficiency**: consumo energético y cómo varía; afecta/es afectado
  por performance, availability, modifiability.
- **Integrability**: capacidad de integrarse con otros sistemas
  (interoperabilidad, costo/facilidad de nuevas integraciones).
- **Modifiability**: capacidad de ser cambiado (qué, qué tan probable, cuándo,
  quién, cuánto cuesta). Incluye Mantenibilidad, Escalabilidad, Portabilidad.
- **Performance**: cumplir requisitos de tiempo — velocidad, uso de recursos
  (CPU, memoria), tiempo de respuesta.
- **Safety**: "no mates a nadie". Criticidad = qué tanto se pierde (vida,
  dinero esencial/discrecional, comodidad) × cantidad de stakeholders
  afectados.
- **Security**: Confidentiality (protección contra acceso no autorizado),
  Integrity (protección contra manipulación no autorizada), Availability
  (disponibilidad para uso legítimo).
- **Testability**: capacidad de ser probado, encontrar errores temprano,
  controlar entradas/salidas de cada componente, reproducir errores previos.
- **Usability**: soporte al usuario, facilidad de aprendizaje, eficiencia de
  uso, minimizar impacto de errores, adaptabilidad, satisfacción del usuario.

## Estilos / patrones arquitectónicos

Layered/N-Tier, Modular Monolith, Pipeline/Pipe-and-Filter, Microkernel,
Service-based, Event-driven, Orchestration-driven Service-Oriented (ESB),
Microservices, CQRS, Broker-domain.

## Trade-offs

- **Teorema CAP**: escoger solo 2 de 3 — Consistency, Availability, Partition
  tolerance.
- Eficiencia energética vs performance / vs availability.

## Recomendaciones generales

- Equipo de arquitectura pequeño.
- Priorizar atributos de calidad → decisiones y trade-offs explícitos.
- Documentación incremental, usando vistas.
- Evaluación temprana de satisfacción de atributos de calidad y trade-offs.
- La arquitectura debe permitir implementación incremental ("esqueleto" +
  "carne").
