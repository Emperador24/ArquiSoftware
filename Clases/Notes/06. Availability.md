# Clase 6 — Disponibilidad (Availability)

## Definición

El sistema está "siempre listo" para llevar a cabo sus tareas cuando se
requiera. Modelo de estados: `Disponible` ⇄ `No disponible`, transición por
`Falla (Failure)` y `Recuperación (Recovery)`.

Cadena causal: **Defecto o avería (Fault)** se manifiesta como **Error** →
conduce a **Falla (Failure)** → se manifiesta con **Interrupción de
servicio**, que persiste durante el **Tiempo de inactividad (Downtime)**. Se
resuelve con **Resiliencia (Resiliency)**: Detección, Recuperación,
Prevención.

## Medición

Fórmula: `Disponibilidad = MTBF / (MTBF + MTTR)`
- **MTBF** (Mean Time Between Failures): tiempo medio entre fallas.
- **MTTR** (Mean Time To Repair): tiempo medio de reparación.

### Service Level Agreement (SLA)
Acuerdo de nivel de servicio que incluye compromiso de disponibilidad. Tabla
de referencia (downtime tolerado):
| Disponibilidad | Downtime/90 días | Downtime/año |
|---|---|---|
| 99.0% | 21h 36m | 3 días, 15.6h |
| 99.9% | 2h 10m | 8h 0m 46s |
| 99.99% | 12m 58s | 52m 34s |
| 99.999% | 1m 18s | 5m 15s |
| 99.9999% | 8s | 32s |

deben o no contar para la fórmula de disponibilidad?

## Tácticas para Disponibilidad (Bass/Kazman)

Tres grupos: **Detect Faults**, **Recover from Faults**, **Prevent Faults**.

### Detección de defectos
Monitoreo (CPU, memoria, I/O), Ping/Echo, Heartbeat (+ variante Watchdog:
reset si no llega el pulso), Timestamp (orden de mensajes), Monitoreo de
condiciones (sensores de hardware: temperatura, humedad, vibración,
checksums), Sanity checking, Voting (comparar respuestas de réplicas),
Detección de excepciones (try-catch, tipado fuerte, timeout), Self-test
(BIOS, routers/switches, colas de mensajes con mensaje "canario",
verificación de integridad en BD).

### Recuperación de defectos
- **Preparación y reparación**: Redundant spare/réplicas, Rollback (BD,
  journaling filesystems, checkpoints), Manejo de excepciones, Actualización
  de software sin afectar ejecución (hotfixes, In-Service Software Upgrade —
  ISSU, combinado con redundant spare), Retry (con máximo de reintentos,
  útil con operaciones idempotentes o protocolos de red con reenvío), Ignorar
  comportamiento defectuoso (cuando el mensaje es solo advertencia), Graceful
  degradation (mantener funciones críticas, degradar las no críticas: ej.
  catálogo genérico en caché en vez de personalizado, bajar calidad de
  streaming, mensaje "servicio temporalmente no disponible"), Reconfiguración
  (reasignar responsabilidades cuando falla una parte, desplegar en menos
  nodos).
- **Reintroducción**: Shadow (dejar el componente corriendo oculto antes de
  reintroducirlo), Resincronización de estado, Reinicio escalado (de hilos →
  proceso → contenedor → VM → máquina física), Nonstop Forwarding (a nivel
  OSI 3: si el Control Plane cae, el Data Plane sigue enviando paquetes con
  las rutas ya calculadas).

### Prevención de defectos
Dar de baja temporalmente (desconectar/reparar/conectar, reiniciar,
apagar/prender), Transacciones (ACID, Two-phase commit, patrón SAGA), Modelo
predictivo (cadenas de Markov, redes de Petri, árboles de fallas, machine
learning), Prevención de excepciones (smart pointers en C++, garbage
collection en Java, ownership model en Rust), Incrementar estados
"competentes" (diseñar el sistema para manejar más flujos alternativos,
tanto normales como de excepción).

## Patrones para Disponibilidad

- **Redundancia**: copias del nodo (activas + repuestos). Determinar caída
  con monitoreo/ping/heartbeat/sanity check/voting; sincronizar estado con
  checkpoints o transacciones.
  - Redundancia activa (hot spare): todos los nodos activos simultáneamente,
    sincronización constante — alto costo, alta disponibilidad.
  - Redundancia pasiva (warm spare): subconjunto activo + subconjunto en modo
    shadow con actualizaciones más esporádicas — costo medio, disponibilidad
    media.
  - Repuesto (cold spare): nodos de repuesto apagados, se encienden al fallar
    el activo — menor costo, baja disponibilidad.
  - Triple Modular Redundancy (TMR): 3+ sistemas redundantes responden a la
    misma operación crítica, respuesta correcta por mayoría (ejemplo:
    aviónica, caso Boeing; automatización industrial).
- **Circuit Breaker**: monitor externo al proceso que controla frecuencia y
  máximo de reintentos (ejemplo: librería Resilience4j).
