# Clase 4 — Notación y vistas arquitectónicas

## Por qué documentar

Tradición oral es frágil (memoria humana olvida, distorsiona, no comunica
bien detalles complejos). La escritura persiste la información, evita
"olvidos", define cuál es la versión "oficial", comunica decisiones a los
stakeholders, guía al equipo de desarrollo y facilita la comprensión del
sistema a quien lo vea por primera vez.

## Nivel de formalidad

- **Informal**: diagramas de cajas y flechas libres (ej. diagramas tipo
  draft1.ai).
- **Semi-formal**: notaciones con reglas — **C4**, **UML**, SysML, ArchiMate.
- **Formal**: Architecture Definition Languages (ADL) — ej. Rapide, Wright,
  con sintaxis de componentes/conectores/configuración totalmente definida.

## Vistas — Modelo 4+1

Diferentes perspectivas de un sistema (como los planos de un edificio):
- **Logical view**: principales conceptos del sistema, modelo de dominio.
  Diagrama: **de clases** (típicamente solo clases del dominio del problema).
- **Process view**: comportamiento del sistema. Diagramas: **de secuencia**,
  **de actividad**, **de estados**.
- **Development view**: cómo está estructurado el código fuente y los
  módulos compilados. Diagramas: **de paquetes**, **de componentes**, árbol
  de carpetas.
- **Physical view**: cómo se instala/despliega el sistema. Diagrama: **de
  despliegue**.
- **Scenarios**: una "vista de procesos" más gruesa, en ciertos casos más
  cercana al lenguaje del cliente. Conecta las otras 4 vistas.

## Modelo C4 (https://c4model.com)

Enfoque liviano, semi-formal, con niveles claramente diferenciados y
relación más intuitiva entre diagramas. Compatible (hasta cierto punto) con
UML.

**Diagramas principales** (jerárquicos, de más a menos abstracto):
1. **System Context Diagram** — el sistema, sus usuarios y los sistemas
   externos con los que interactúa.
2. **Container Diagram** — las unidades desplegables (apps, APIs, bases de
   datos, etc.) dentro del sistema.
3. **Component Diagram** — subconjuntos de un contenedor que proveen una
   interfaz (ej. los componentes internos del backend).
4. **Code Diagram** — diseño detallado (clases/interfaces de un componente).

**Diagramas auxiliares**:
- **System Landscape Diagram** — vista más amplia con varios sistemas de la
  organización (no solo el sistema en cuestión).
- **Dynamic Diagram** — cómo colaboran los elementos para un caso de uso
  específico (similar a un diagrama de secuencia).
- **Deployment Diagram** — cómo se despliegan los contenedores en nodos de
  infraestructura reales (servidores, contenedores Docker, VMs, etc.).

**Elementos de notación**:
- Nodos: título, tipo de nodo + tecnología, descripción, forma/color/íconos.
- Flechas: etiqueta (debe formar una frase, ej. "Makes requests to") +
  tecnología/protocolo.

### C4 vs 4+1

| C4 | 4+1 |
|---|---|
| Context Diagram, System Landscape Diagram | ~ Scenarios |
| Container Diagram | Development View |
| Component Diagram | Development View |
| Code Diagram | Logical View |
| Deployment Diagram | Physical View |
| Dynamic Diagrams | Process View |
