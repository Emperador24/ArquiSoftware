# Clase 13 — Comprobabilidad (Testability)

## Definición

Facilidad de un sistema para demostrar sus fallos: probabilidad de que un
sistema falle en la siguiente prueba, dado que tiene una falla.

### Requisitos
- Posibilidad de controlar entradas.
- Posibilidad de observar salidas.
- Posibilidad de observar su estado interno (antes, durante y después de
  cada prueba).

## Tácticas de Comprobabilidad (Bass/Kazman)

Dos grupos: **Control and Observe System State**, **Limit Complexity**.

### Controlar y observar el estado del sistema
- **Interfaces especializadas**: getters, setters, reportar estado completo
  de un objeto, resetear el estado del objeto, logging.
- **Record/playback**: guardar y reproducir cambios de estado en el
  sistema. Ejemplos: LiveRecorder, RevDebug, Java Flight Recorder (JFR), RR
  (C++), OpenReplay.
- **Localizar (factorizar) el almacenamiento del estado del sistema**:
  implementar máquinas de estados en el código.
- **Sandboxing y abstracción de fuentes de datos**: aislar el componente del
  mundo real — virtualización, mocks, fuentes de datos simuladas.
- **Uso de `assert` en ejecución**: pre-condiciones, post-condiciones e
  invariantes.

### Limitar complejidad
- **Reducir complejidad estructural**: reducir acoplamiento, reducir
  profundidad de herencia, reducir polimorfismo, aumentar cohesión.
- **Reducir no-determinismo**: controlar paralelismo (ej. condiciones de
  carrera).

## Patrones de Comprobabilidad

- **Inyección de dependencias (Dependency Injection)**: asegurar que todas
  las dependencias de una clase se puedan parametrizar desde su constructor,
  en vez de instanciarlas internamente ("classic programming" sin DI).
  Ejemplo comparado en el deck: `DataProcessor` que instancia
  `XMLPersistence` internamente (no testeable/flexible) vs. `DataProcessor`
  que recibe `Persistence` por constructor (testeable con mocks).
  - Ventaja: flexibilidad para cambiar comportamiento del sistema (permite
    usar Mocks en pruebas).
  - Desventajas: complejidad adicional, curva de aprendizaje.
- **Patrón estrategia**: interfaz abstracta con implementaciones concretas
  para diferentes algoritmos.
  - Ventaja: unificación de interfaces.
  - Desventajas: ligero aumento de complejidad, a veces hace más difícil la
    depuración.
- **Filtros de intercepción**: código que intercepta una petición para
  extraer información útil para testing.
  - Ventajas: aumenta cohesión, reduce acoplamiento, factoriza código de
    logging y auditoría.
  - Desventaja: overhead.
