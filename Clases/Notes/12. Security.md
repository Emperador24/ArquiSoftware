# Clase 12 — Seguridad (Security)

## El problema: control de acceso

**Control de Acceso**: "Limitar el acceso a recursos de un sistema de
información sólo a usuarios, programas, procesos u otros sistemas
debidamente autorizados" (Glosario ATIS Telecom). El deck introduce el tema
con ejemplos históricos de control de acceso físico (candados, cajas
fuertes) y criptografía (máquina Enigma).

## Riesgos en seguridad de la información (tríada CIA)

**Disponibilidad, Confidencialidad, Integridad**. Mecanismos asociados:
- Disponibilidad ← Redundancia, Resiliencia.
- Confidencialidad e Integridad ← Canales seguros, **Control de acceso**,
  Funciones de hashing, etc.

## Control de acceso

Se compone de:
- **Autenticación**: determina que la identidad del usuario es legítima.
  Factores: algo que el usuario conoce (contraseñas), algo que el usuario
  tiene (tarjeta de identificación, clave privada en criptografía
  asimétrica), algo que el usuario es (biometría).
- **Autorización**: determina qué acciones puede o no hacer el usuario
  (permisos/privilegios). Depende de la autenticación. Modelo: Usuario →
  Sesión → Sujeto → Operación → Objeto, con Permiso asociado a
  Operación+Objeto dentro del Sistema.

### Principio de mínimo privilegio
Asignar al usuario los mínimos privilegios requeridos para que cumpla
adecuadamente sus responsabilidades.

### Modelos de control de acceso
- **Mandatory Access Control (MAC)**: niveles jerárquicos de clasificación
  (Top Secret > Secret > Confidential > Unclassified); un usuario con nivel
  S puede acceder a documentos Secret pero no a los de nivel superior
  (referencia: Bell & LaPadula, 1976).
- **Discretionary Access Control (DAC)**: permiso para asignar permisos a
  otros usuarios (referencia: DoD Trusted Computer System Evaluation
  Criteria, 1985).
- **Role-Based Access Control (RBAC)**: usuario → rol(es) → permiso(s)
  (referencias: Ferraiolo & Kuhn 2003; Ferraiolo, Sandhu, Gavrila,
  Chandramouli 2001 — estándar NIST). Ejemplo dado: rol Profesor → permisos
  "Calificar estudiante" y "Subir documento"; rol Estudiante → permisos
  "Subir documento" y "Personalizar página inicio".

## Tácticas de Seguridad (Bass/Kazman)

Cuatro grupos: **Detect Attacks**, **Resist Attacks**, **React to Attacks**,
**Recover from Attacks**.

### Detectar ataques
- Detectar intrusión / detectar denegación de servicio: escanear tráfico de
  red, detectar patrones sospechosos.
- Verificar integridad de mensajes: checksums, hashing (ej. checksums de
  downloads de Linux).
- Detectar anomalías en transmisión de mensajes: buscar patrones que
  evidencien "man-in-the-middle" (timing, conexiones fallidas, etc.).

### Resistir ataques
- **Identificar actores**: origen de conexiones — ID de usuario, IP,
  protocolos, fingerprinting (ej. amiunique.org/fingerprint).
- **Autenticar actores**: password, tokens, 2FA, CAPTCHA.
- **Autorizar actores**: limitar acceso a recursos según usuario o rol.
- **Limitar acceso**: restringir puntos de acceso (IP, tipo de tráfico).
- **Limitar exposición**: reducir cantidad de recursos accesibles desde un
  mismo punto de acceso — principio de mínimo privilegio, desactivar
  puertos no utilizados, API Gateway.
- **Cifrar datos**: criptografía simétrica y asimétrica (ej. Diffie-Hellman
  key exchange).
- **Separar entidades**: separación física (sub-redes distintas), VM y
  contenedores, air gaps.
- **Validar entradas**: prevenir datos maliciosos, sanitizar entradas (SQL
  Injection, Cross-side scripting/XSS).
- **Cambiar configuración por defecto de credenciales**: ej. no dejar
  user "admin"/password "password".
- **Secure coding** (referencia externa enlazada en la diapositiva).

### Reaccionar a ataques
Revocar acceso (incluso a usuarios legítimos), restringir login tras un
número de intentos, informar a los actores en caso de un ataque.

### Recuperarse de ataques
Todas las tácticas de recuperación de Availability, más:
- **Auditar**: logging — registro de acciones de cada usuario y sus
  resultados.
- **No repudiación**: asegurar que las partes de una comunicación no
  puedan negar su participación (ej. compra online: comprador y vendedor no
  pueden negar la transacción).

## Patrones de seguridad

- **Interceptor de validación**: intercepta mensajes, valida
  integridad/autenticidad, detecta intrusiones/denegación de servicio.
  Ejemplo: Spring Security Interceptors. Ventaja: protege de muchos ataques.
  Desventajas: overhead, costos de mantenimiento.
- **Sistema de prevención de intrusiones (IPS)**: componente que monitorea
  el sistema para identificar actividades sospechosas. Ejemplos: Snort,
  Suricata, Zeek, OSSEC.
