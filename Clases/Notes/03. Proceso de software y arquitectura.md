# Clase 3 — Proceso de software y arquitectura

## Ingeniería de software: personas + procesos + herramientas

- **Tradicional (cascada)**: entender problema → diseñar → construir →
  probar → implantar → mantener, en secuencia.
- **Por qué falla**: los requisitos no se conocen completamente de entrada
  (clientes inseguros de lo que quieren, detalles solo se revelan durante el
  desarrollo, opiniones cambian al ver el producto, fuerzas externas
  empujan cambios). Cf. Clements & Parnas, "A Rational Design Process: How
  and Why to Fake It" (1986).
- **Desafíos**: requisitos cambiantes, rapidez de cambio, complejidad
  (técnico) + comunicación, disciplina, adaptabilidad, confianza (humano).
- **Iterativa e incremental**: mismo ciclo pero repetido; iteraciones de 1-6
  semanas, cada una un "mini proyecto de software" que entrega valor
  incremental hasta la entrega final al cliente.
  - Distribución de esfuerzo por iteración: Requerimientos decrece,
    Diseño tiene pico intermedio, Implementación y Testing crecen y se
    mantienen altos hacia el final.
  - Cono de incertidumbre [McConnel 1998]: el rango de estimación de
    costo/esfuerzo/calendarización se reduce con el tiempo.
- **Contratos de costo fijo**: ejecutar en dos etapas — exploración (reduce
  incertidumbre) y construcción.

## Métodos ágiles

Iterativos e incrementales, más livianos y veloces, generación temprana y
frecuente de valor, foco en el factor humano. Ejemplos: Scrum, XP, DAD.

Propiedades esenciales [Cockburn 2004]: entregas frecuentes, mejoramiento
reflexivo, comunicación, seguridad personal, concentración, fácil acceso a
usuarios expertos, DevOps.

Ciclo: ítems de trabajo → planeación de iteración → iteración (reuniones
diarias + tareas) → entrega → presentación al cliente → retrospectiva →
actualización de ítems de trabajo.

**DevOps** = Administración de configuración + Pruebas automáticas +
Integración frecuente. Flujo: Requerimientos → Diseño → Implementación →
Pruebas unitarias → Pruebas de integración → Empaquetamiento → Despliegue de
prueba → Pruebas de sistema y aceptación → Despliegue en producción →
Operaciones → Monitoreo (retroalimenta a Requerimientos).

## Roles ("gallina y cerdo")

Dueño del producto, Administrador/Líder de proyecto, Ingeniero de requisitos,
Arquitecto de software, Equipo de desarrollo (Programador, Tester, Diseñador
BD, Diseñador UI/UX), Otros (Ingeniero de procesos, Escritor técnico,
Diseñador gráfico).

- **Arquitecto vs Administrador**: el arquitecto apoya al administrador en
  Integration, Scope, Time, Cost, Quality, Human Resources, Communications,
  Risk, Procurement (áreas PMBOK).
- **Arquitecto vs Ing. de requisitos**: el ing. de requisitos entrega
  requisitos funcionales/no funcionales; el arquitecto los prioriza y
  analiza trade-offs para producir los ASR.
- **Arquitecto vs Equipo de desarrollo**: el arquitecto lidera el diseño
  arquitectónico (componentes, conexiones, comportamiento, despliegue); el
  equipo debe adherirse a lo que indica.
- **Arquitecto vs stakeholders**: valida la arquitectura junto al dueño del
  producto.

## Arquitectura y ciclo de vida

- **BDUF** (Big Design Up Front, cascada): la arquitectura se establece al
  inicio y no cambia.
- **Emergente** (ágil puro): arquitectura creada por incrementos, versión
  final solo al terminar el proyecto.
- **Iteración 0** (alternativa balanceada): pico inicial de diseño más alto
  que el enfoque emergente puro, seguido de refinamiento incremental — este
  es el enfoque recomendado para el curso.

Comparación Arquitectura vs Principios Ágiles: compatible en casi todo,
excepto que para sistemas complejos **la documentación sí es esencial** (no
solo interacción cara a cara) y **se requieren personas capacitadas /
organización más formal** (no solo equipos auto-organizados).
